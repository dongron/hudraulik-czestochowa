## Overview

Show the weekly opening hours (Mon to Sat open 24h, Sunday closed) in the contact section. Publish the same hours in the home page's embedded business data (schema.org `Plumber`). Remove every "24/7 / weekend" claim that contradicts them. The hours live in one owner-editable place in Sanity `settings`, so the visible block and the business data can never drift apart. The goal is to make the website a consistent, trustworthy source that backs up the Google Business Profile against false "temporarily closed" suggestions.

## Architecture Decisions

1. **Hours stored as one object with seven fixed day fields** (`openingHours.monday ... .sunday`) in `settings`, each a small `dayHours` object: `mode: 'open24' | 'closed' | 'hours'` plus `opens` / `closes` (`HH:MM`, only shown when `mode === 'hours'`).
   *Why:* fixed fields guarantee exactly one entry per day in the right order, with no duplicate/missing-day validation. The `mode` radio makes "open 24h" and "closed" explicit instead of relying on magic times like `00:00-23:59`.
   *Rejected:* an array of day entries (needs uniqueness validation and ordering logic); `schema.org` shorthand strings like `Mo-Sa 00:00-23:59` (not editor-friendly).

2. **One pure helper module, `frontend/app/lib/openingHours.ts`**, used by both consumers:
   - `toDisplayRows(hours)` returns 7 rows `{day: 'Poniedziałek', label: 'Otwarte całą dobę' | 'Nieczynne' | '08:00–16:00'}`, or `[]` when hours are not set.
   - `toOpeningHoursSpecification(hours)` returns schema.org `OpeningHoursSpecification[]`, or `undefined` when hours are not set.
   *Why:* this satisfies FR-008 (single source), keeps the components dumb and makes the mapping unit-testable without rendering.

3. **schema.org encoding follows Google's documented conventions**: open 24h is `opens: '00:00', closes: '23:59'`, and closed all day is `opens: '00:00', closes: '00:00'`. Days with identical hours are grouped into one spec entry (Mon to Sat together, Sunday separate). Sunday is published **explicitly as closed** rather than omitted, so it reads as "closed", not "unknown" (spec edge case).

4. **New top-level `settings.websiteUrl` field (url, required)** is used for schema.org `url`, and `googleMapsUrl` moves to `hasMap`.
   *Why:* `ogImage.metadataBase` is semantically the OG base URL, is nested under the image and holds junk in the draft. A request `host` header (as `sitemap.ts` does) varies between preview and production. An explicit field is the least surprising option.

5. **Emergency wording stays static text, rewritten** to "Pogotowie całą dobę, pon–sob" (hero) and "Pogotowie hydrauliczne całą dobę od poniedziałku do soboty" (contact note). The `emergencyAvailable` toggle is unchanged.
   *Why:* the spec keeps the toggle and only fixes the wording. Deriving the text from the hours adds logic for a case (changed hours) that the owner would notice anyway. This trade-off is flagged in Risks.

6. **The hours block renders inside `LandingContact`, directly after the Phone/Address entries**, as a `<dl>` (day as `<dt>`, hours as `<dd>`), so screen readers announce day/hours pairs (FR-004). It is hidden when `toDisplayRows` returns `[]` (FR-010). It is independent of `emergencyAvailable`.

7. **Content changes go through Sanity MCP** (`deploy_schema`, `patch_documents`, `publish_documents`), the same method used in 001 and 004. These are outward-facing writes, so each one needs your explicit go-ahead at implementation time.
